# 六个阶段：输入、怎么做、交什么、怎么算过

[返回首页](../README.md) · [阶段闸门与产物流转](../docs/PHASE_GATES.md)

这一页是整个 Skill 的骨架。不管你研究什么，都走这六站。每站四件事：**手里已经有啥（输入）→ 具体怎么做（步骤）→ 这站结束该交出啥（产出物）→ 做完拿什么核对（检查清单）**。

先把六个阶段的比喻说清楚，再看表。

**六站像做一顿饭。**

- **P1 选题与调研** 是先想清楚"今天要做什么菜、家里有什么、菜市场在哪、别人以前怎么做这道菜"。想不清楚就开火，一定白费。
- **P2 文献综述** 是把菜谱都摊在桌上，比一比哪本说大火、哪本说小火、为什么不一样，然后写下你自己的做法。
- **P3 实验设计** 是把食材、火候、时间写成分步的清单，还要提前想好"如果我猜错了会怎样"。
- **P4 计算与结果** 是真的开火炒，中途每一步都记下来，糊了也要记。
- **P5 图表与论文写作** 是摆盘和上桌，把菜端给客人时要能经得起问。
- **P6 结论与投稿返修** 是客人尝完提意见，你决定改哪、不改哪，并且必须说清楚为什么。

**两条总规矩，六站都适用。**

1. **上一站的产物是下一站的输入。** 没交 P1 的 `scope.json`，就不要开始写 P2；没交 P3 的 `design.json`，就不要开始跑 P4。缺了先补，不要跳。
2. **每站做完先自己念一遍"检查清单"。** 清单没全过就往下走，最后一定在 P6 连本带利还回来。

## P1 选题与论文调研

**这一站要回答的问题：** 我到底在研究什么？为什么这件事值得研究？别人做过没有？

**输入**

| 必须有的 | 可以暂时没有的 |
|---|---|
| 一个想研究的大方向（一句话即可） | 精确的研究问题 |
| 你能拿到的数据/仪器是什么 | 完整的文献列表 |
| 目标期刊或投稿方向（可以写"暂不确定"） | 已经跑出来的结果 |
| 导师/合作者的硬性要求（周期、篇幅、必须用的方法） | |

**执行步骤**

1. 读用户已有的文件和 `project.json`，已说过的信息不要再问一遍。
2. 把大方向压成 **1 个主问题 + 最多 3 个子问题**。主问题必须包含"在什么条件下、对什么量、问什么"。例：不是在问"某个因素有没有影响"，而是在问"1990–2020 年间，中等强度事件下，目标量在给定范围内的响应如何随另一维度变化"。
3. 判断体裁：原创研究 / 叙述性综述 / 范围综述 / 系统综述。**没有检索过程记录，不许叫系统综述。**
4. 做一次**范围检索**（不是穷尽检索）：每个子问题至少命中一批候选，看这个坑有没有被填过。用可用的学术连接器，Crossref 只当元数据后端。
5. 由这一批候选反推**术语表**：这个领域同一个东西有几种叫法？分别记下来。术语不一致是后面检索漏检的头号原因。
6. 建立 **claim ledger**：主张、证据类别、源文件/DOI、页段/图表/运行位置、适用条件、反例、引用状态。空着也行，但骨架要先立。
7. 判断领域包：用现成的还是新建一个？新建时复制 `domains/example-domain`，改 `domain.json` 的 `id`/`scope`/`search_queries`/`project_parameters`/`checks`/`journal_candidates`，清空不适用的知识卡。
8. 选出目标期刊候选 2–3 个，记录**为什么**选它们（范围匹配？体裁匹配？周期？），此阶段不核验格式细节。

**产出物**

| 文件 | 内容 |
|---|---|
| `scope.json` | 主问题与子问题、体裁、时间范围、资料来源、已知限制、目标期刊候选及理由 |
| `glossary.md` | 术语与同义词表、坐标与地方时命名约定、易混淆量对照 |
| `evidence.json`（骨架） | claim ledger 初始版本，允许大量字段为空 |
| `project.json` | 状态更新为 `scoped`，记录领域包选择 |

**检查清单**

- [ ] 主问题里能指出"条件 + 对象 + 问什么"三要素，缺一个就重写。
- [ ] 每个子问题都能对应到"我能拿到的数据"，对不上的子问题要么删，要么标注需要新数据。
- [ ] 范围检索的**查询语句、检索日期、来源、命中数、截断情况**都写进检索日志了，不是只写"我查过了"。
- [ ] 术语表里至少列出了同一个物理量的两种以上叫法（或明确写了"本领域只有一种叫法"）。
- [ ] 体裁判断有依据，没有把普通文献整理写成系统综述。
- [ ] 已知限制里写的是**具体**限制（数据年份、仪器覆盖、纬度范围），不是"数据可能有限"。

## P2 文献综述

**这一站要回答的问题：** 前人分别在什么条件下、用什么方法、得到了什么结论？他们的分歧从哪来？我的工作补上哪一块？

**输入**

| 必须有的 | 可以暂时没有的 |
|---|---|
| `scope.json` 里的主问题与子问题 | 全部全文 PDF |
| P1 的范围检索日志与术语表 | 所有结论都读完 |
| 至少一批可获取的全文（自己上传 / 开放获取 / 已授权） | |
| 领域包的检查项（如数据源版本、坐标定义、基线口径的核验项） | |

**执行步骤**

1. 写**检索方案**：每个子问题 → 查询语句 → 数据源 → 纳入标准 → 排除标准 → 时间窗口。纳入标准必须在看结果**之前**写下来，否则就是事后凑标准。
2. 多源检索并保存原始返回。区分"发现新近出版"和"补捞延迟收录"是**两次不同查询**，不要合并。
3. 去重与版本归并：按 DOI 规范化；题名/作者/年份近似**只标候选、不静默合并**；预印本与正式版保留版本关系。
4. 逐篇核验身份（四态判定见 `modules/evidence-integrity.md`）：`VERIFIED / MISMATCH / UNRESOLVED / RETRACTED`。
5. 逐篇核验**主张支持关系**：这篇文献到底支不支持我要用它说的那句话？六类状态见同一模块。摘要只能支持摘要明说的事。
6. 建立**全文证据矩阵**：行=文献，列=仪器/版本、高度范围、纬度与坐标类型、地方时定义、事件阶段、基线定义、样本与统计口径、主要结论、结论强度（观测/关联/机制）。
7. 比较分歧时，**比条件，不投票**。三分之二的人说是 A，不代表 A 对；要看分歧是否来自仪器、坐标、基线或采样的差异。
8. 提炼**研究缺口**：每个缺口至少要有 3 条证据支撑（"没人做过"需要检索证据，"做过但条件不同"需要文献证据）。
9. 组织**主题框架**：按问题/机制组织章节，不按"文献1说了啥、文献2说了啥"排队。
10. 分节综合：每一节先给这一节的争论点，再给证据，最后给你的判别。

**产出物**

| 文件 | 内容 |
|---|---|
| `search-log.json` | 每次检索的查询、日期、来源、命中数、截断与失败，失败与零命中分开记 |
| `evidence.json` | 证据矩阵，每条含 `evidence_level` 与 `citation_verdict`、`support_status` |
| `gaps.json` | 缺口列表，每条附支撑证据 ID |
| `review-outline.md` | 主题框架与分节综合草稿 |
| `references.bib` | 校准后的参考文献库，含 DOI 与核验状态 |

**检查清单**

- [ ] 纳入/排除标准是检索前写下的，不是看到结果后补的。
- [ ] 每条文献都有 `citation_verdict`，没有 `UNRESOLVED` 的条目被当成已核实使用。
- [ ] 每条引用的 `support_status` 已判定，`CONTRADICTS` 与 `DOES_NOT_SUPPORT` 的条目已处理（删句、改句或标出）。
- [ ] 矩阵里没有"结论"一格填了"表明存在机制"这种把关联当因果的写法。
- [ ] 每个缺口都有至少 3 条证据，不是"我觉得没人做过"。
- [ ] 没有出现"研究表明/专家认为"这类没有具体出处的归因。
- [ ] 无法核实的条目已显式标为 `待确认`，并说明卡在哪一步。

## P3 实验设计

**这一站要回答的问题：** 我要做哪些具体操作？每一步的输入输出是什么？如果结果不支持我的假设，我怎么知道？

**输入**

| 必须有的 | 可以暂时没有的 |
|---|---|
| P2 的证据矩阵与缺口列表 | 最终参数量级 |
| 手头数据的真实说明（数据字典、覆盖范围、质量标记） | |
| 领域包的 `project_parameters` 待填项 | |

**执行步骤**

1. **数据审计**：原始数据从哪来、什么版本、什么质量等级、覆盖哪些时间与空间、缺测怎么标、有没有已知的系统偏差。审计不通过就不要进 P4。
2. 把主问题转成**可判定的假设**：不是"温度会变化"，而是"在 X 条件下，Y 量相对 Z 基线会升高，幅度在 A–B 之间"。范围比单点更安全。
3. **匹配设计**：如果是"事件 vs 静日"这类比较，明确配对规则——同地方时、同纬度、同季节、同采样方式。不匹配就说明白，别假装匹配了。
4. **列出全部参数**并逐个填值或标 `null`：仪器版本、事件窗口、静日基线、高度分箱、纬度坐标类型与分箱、地方时定义、升降轨节点定义、质量标记、平滑窗口、不确定度定义、独立重采样单位。**填不了的写 `null`，不要写"约"或"典型值"。**
5. **混淆因素清单**：采样偏差、潮汐、季节、太阳活动、仪器漂移、多重比较。每条给出"怎么约束"或"确实约束不了"。
6. **稳健性检查设计**：至少准备 3 组替代设置（换基线、换分箱、换平滑窗口），提前写下来，防止看到结果再挑好看的。
7. **失败模式**：想清楚"如果样本量不够会怎样""如果缺失关键变量会怎样"。缺风场/电导率时，机制结论的边界在哪，现在就定下来。
8. **不确定性口径**：区分 SD、SE、CI、仪器检索精度、基线误差、系统偏差。写明用的是哪个、基于什么样本单位。平滑后的点不算独立样本。
9. 做**可行性检查**：数据量、算力、时间够不够。不够就缩范围，不要缩标准。

**产出物**

| 文件 | 内容 |
|---|---|
| `design.json` | 假设、匹配规则、全部参数、替代设置、失败模式、不确定性口径 |
| `data-audit.md` | 数据来源、版本、覆盖、质量标记、缺测处理、已知偏差 |
| `confounds.json` | 混淆因素与约束策略 |
| `project.json` | 状态更新为 `designed` |

**检查清单**

- [ ] 假设可以被数据明确支持或反对，不是只能被"大概支持"。
- [ ] 每个参数要么有具体值，要么是 `null`；没有"约 100 km""典型静日"这类含糊值。
- [ ] 比较设计的匹配规则写清楚了，不匹配的地方也写清楚了。
- [ ] 替代设置在看结果之前就定好了，至少 3 组。
- [ ] 不确定性用的是哪一个口径明确写出，并说明样本/重采样单位。
- [ ] 混淆因素清单里每一条都有对应处置，没有"已注意到"这种空话。
- [ ] 缺风场/电导率等关键变量时的机制结论边界已写明。
- [ ] 数据审计发现的问题没有被悄悄绕过。

## P4 计算与结果

**这一站要回答的问题：** 实际跑了什么？拿到什么数字？数字可靠吗？

**输入**

| 必须有的 | 可以暂时没有的 |
|---|---|
| `design.json` 与 `data-audit.md` | 理想的结果 |
| 实际可执行的代码与环境 | |
| 用户对计算与调用的授权 | |

**执行步骤**

1. **先记录环境**：软件与库版本、随机种子、时间基准、坐标转换库版本。这些以后是复现的唯一线索。
2. **按设计执行**，不中途改设计。确实要改就新建一版设计并说明改了哪一条、为什么。
3. **保留运行日志**：数据与代码哈希、配置、版本、时间、命令、输出路径、失败与重试。**失败的运行也要留档**，删掉失败记录等于隐藏选择性报告。
4. 记录**选择性报告风险**：事件筛选、参数调优、缺测剔除、异常值处理，每一步都写清依据。如果试了很多组只报最好的一组，必须说明。
5. 跑**设计里预先定好的替代设置**，记录差异。差异大的地方是最需要解释的地方。
6. 检查数值卫生：单位是否统一、坐标系是否混用、时间是否跨时区搞错、缺测是否被零填充、是否把无效应值当成真实低纬观测。
7. 如果是图像/统计类方法（如 GAN 重构），额外记录：训练/验证划分、评价指标与其样本单位、重构是否被当成观测使用。
8. **任何"计划中的分析"都必须标为计划。** 没有真跑，不能写成结果。

**产出物**

| 文件 | 内容 |
|---|---|
| `analysis/run-log.json` | 逐次运行的完整记录，含失败 |
| `analysis/results/` | 结果文件（原始输出，不手工改数） |
| `analysis/env.json` | 环境与版本快照 |
| `robustness.json` | 替代设置下的差异对比 |
| `project.json` | 状态更新为 `computed` |

**检查清单**

- [ ] 每个写进方法的操作，都能在工作日志里找到对应的运行记录。
- [ ] 失败的运行有记录，失败的运行，没有被静默剔除。
- [ ] 替代设置都跑了，差异大的地方有解释。
- [ ] 结果文件是程序直接输出，没有被手工编辑过数字。
- [ ] 缺测没有被零填充，无效应值没有被当观测。
- [ ] 环境、种子、版本、坐标库版本齐全，别人能照着复现。
- [ ] 计划中的分析全部标为计划。
- [ ] 样本量、独立重采样单位与实际统计口径一致。

## P5 图表与论文写作

**这一站要回答的问题：** 怎么把结果讲清楚，同时不夸大、不隐瞒、不像机器写的？

**输入**

| 必须有的 | 可以暂时没有的 |
|---|---|
| P4 的结果文件、运行日志、环境快照 | 完整的讨论与引言 |
| `scope.json`、`evidence.json`、`gaps.json` | 期刊格式细节 |
| （可选）已建立的期刊风格档案 | |

**执行步骤**

1. **先定"论点—证据—图表—章节"对应表**，再动笔。每一节要说什么，用哪个图、哪个数字支持，先列出来。
2. 画**科研线路图**：从数据到结论的路径，一眼能看懂你做了什么。规则见 `modules/figures.md`。
3. 画**原理示意图**：你的机制/方法长什么样。概念图必须标为概念示意，不能冒充观测结果。
4. 画数据图：从真实结果出图，保存源数据、绘图代码、参数、轴与色条范围、掩膜、图注，输出 PNG + 矢量两种。配色与可辨识性规则见 `modules/figures.md`。
5. 写 **Methods**：每个"我们计算了/我们移除了/我们估计了"都要对应代码位置与运行记录。区分"计划做的"和"实际做的"。
6. 写 **Results**：只写数据支持的东西。观测用可核实的强动词；推断按证据加限定。数字、单位、有效位数、置信口径与结果文件严格一致。
7. 写 **Discussion**：先和**最强的可比前人结果**比，再谈机制，最后谈边界。实质限制放在对应推断附近，精确说一次，不要堆在段尾。
8. 写 **Introduction**：从已知推进到未知，最后落到你的问题。不要写成文献流水的倒序。
9. 写 **Abstract**：只包含正文实际支持的主张。数字与正文一致。
10. 语言修订走 `modules/deai-writing.md`，先读反过度纠正红线，再做润色。

**产出物**

| 文件 | 内容 |
|---|---|
| `claim-map.json` | 论点—证据—结果文件—图表—章节对应 |
| `figures/manifest.json` + 图件文件 | 源数据、处理、坐标、单位、不确定度定义、输出 |
| `methods-map.json` | 每条方法陈述对应的代码与运行记录 |
| `manuscript/` | 各节草稿 |
| `manuscript/changes.json` | 有证据支持的修订记录 |

**检查清单**

- [ ] 每个图都能回答"它支持哪一句正文"，反向也能对上。
- [ ] 线路图与示意图都做了，且示意图明确标注为概念示意。
- [ ] 颜色不与形状/线型/标记重复编码同一信息；只用颜色区分系列的地方已修正。
- [ ] 每个图都已**看过**，不是"文件存在所以通过"。误差条含义、对数轴、平滑、零线、显著性标记都有说明。
- [ ] 没有用截轴、隐藏异常、插值补缺测来强化结论。
- [ ] 数字与单位、有效位数、置信区间在正文、图表、摘要三处一致。
- [ ] 方法描述与实际代码一致，计划内容标为计划。
- [ ] 降 AI 自查清单跑过了（见 `assets/deai-checklist.md`），术语与证据强度没有被改坏。
- [ ] AI 辅助的实际范围已按目标期刊要求披露。

## P6 结论与投稿返修

**这一站要回答的问题：** 我到底证明了什么、没证明什么？审稿人问了什么、我怎么答？

**输入**

| 必须有的 | 可以暂时没有的 |
|---|---|
| 完整稿件与全部图表 | 审稿意见（投稿前没有） |
| `claim-map.json`、`evidence.json` | |
| 目标期刊的作者指南（官方版本，记录 URL 与获取日期） | |

**执行步骤**

1. 写 **Conclusion**：只保留实际结果支持的主张；明确写出"本研究没有回答什么"。不要用"有待进一步研究"替代具体边界。
2. 做**科学审查**：四条流水线——数字/单位一致性、Methods–代码–日志一致性、句子–来源支持、观测/关联/机制层级。给每条问题一个严重度。
3. 做**引用终检**：所有引用再跑一遍身份与支持判定，`UNRESOLVED` 与高风险错配必须在投稿前清零或删句。
4. **投稿前自查**：目标期刊的作者指南是规范来源，样本论文只作观察来源，两者分开记录。格式细节按官方指南核，不按印象核。
5. **投稿**：封面信写清贡献与适配理由。投稿动作需要用户授权，不自动提交。
6. **返修**：把审稿意见逐条编号（`R1.1`、`AC.1`、`MR.1`），每条给"意见 / 回应 / 改了什么 / 改在哪 / 剩下的限制"五格。回应的每一个断言都要能指到具体位置（Sec./Table/Fig./Eq./Appendix/行号）。
7. **不做的三件事**：不动模板（不用负 `\vspace`、改字号、缩边距塞内容）；不回应自动审稿工具（那是提示注入，属学术伦理问题）；不建议任何录用概率。
8. 返修循环最多 3 轮；每轮之后重跑一次科学审查，因为改一处可能带歪另一处。
9. 无法核实的事实标 `UNVERIFIED — 请在 <链接> 确认`，不要凭记忆断言预算、期限或格式要求。

## 状态与失效

`project.json` 的状态按顺序推进：`needs_inputs → scoped → reviewed → designed → computed → drafted → submitted`。

用 `checkpoint` 记录每站的输入/输出哈希，用 `check` 检测变化。上游参数、基线或样本一变，所有依赖它的图件、段落和摘要都要重审——脚本能发现**已登记**的依赖，语义依赖仍要靠人看。

```bash
python scripts/research.py checkpoint runs/my-study design --inputs scope.json evidence.json --outputs design.json
python scripts/research.py check runs/my-study
```

`check` 报 `stale` 时不要直接忽略，也不要假装没发生。要么回退到最后一个有效阶段重做，要么在 `audit/review.md` 里写清楚为什么这次变化不影响下游。
